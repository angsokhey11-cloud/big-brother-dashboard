# Android bundled source preparation — architecture decision pending
The current Java-native prototype in native-mobile-v2 is preserved. No existing APK is replaced, no Android WebView or renderer is added by this preparation commit, no production or Local changes.
Inspected the Online Android MainActivity (remote GitHub Pages WebView), PWA entry points mobile.js, mobile-main-menu-stockcontrol-v5.js, mobile.html, index.html, sw.js on main, and working Windows desktop README, tools/bundle_web.py, config/modules.lock.json, and src/MainWindow.cs. The Windows app bundles 32 pinned source repositories, rewrites first-party GitHub Pages references to its local virtual HTTPS origin, and uses WebView2 for local rendering. All 29 repository names directly referenced by the inspected PWA entry points occur in that lock. This is not an exhaustive transitive dependency or every-file inspection.
This folder contains the original desktop lock, a build-time bundler adapted to also require the mobile entry point, and source inventory. Running python tools/bundle_web.py from this folder creates build/web and a bundle-report; GitHub is needed at build time only. The script has not been executed for Android in this commit. It uses the desktop pinned snapshot; refresh pins and audit dynamic origins, third-party assets, service workers, bridges, camera, printing, storage, notifications and permissions before any Android integration. No financial writes occur in the bundler.
Two possible runtime architectures: locally bundled web rendering (same as desktop, Android WebView renders installed files and must block remote GitHub Pages UI loads), or pure Android native (no WebView at all; requires porting JavaScript/HTML/CSS interactions). The former preserves existing frontend implementation much more directly. Confirm the rendering requirement before selecting one. Existing native builds remain independent.
